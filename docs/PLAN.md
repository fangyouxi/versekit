# 项目规划与审阅

**版本** 2026-10-27　**作者** 产品 + 架构（联合审阅）　**前提文档** `PRD.md` · `ARCHITECTURE.md` · `adapter-contract.md` · `platforms.md` · `adr-0001-reuse.md`

---

## 1. 产品目标（一页）

**一句话**：让一个人管住自己所有平台的发布与数据 —— 电脑干活，手机拍板。

**北极星指标**：每周成功完成的 `publish` 数（含 notify 模式下用户确认的）。
它不是"安装量"，因为安装不产生价值；也不是"发布成功率"，因为它可以通过少发来作弊。

**三个可验证的承诺**（对外可以这么讲，任何一条不成立就不能发版）：

| # | 承诺 | 验收方式 |
|---|---|---|
| G1 | 首次价值 < 30 分钟（装好 → 第一条真的发出去） | 找 3 个真实创作者盲测 |
| G2 | 一条内容发 5 平台 < 2 分钟（含差异编排） | 计时演示，录屏 |
| G3 | 账号失效**永远**由系统先发现，而不是用户自己发现 | 断网/改密演练，检查事件与卡片 |

**不做**（PRD §2 已定，此处只强调一条）：不采集公开内容、不做内容生产、不做托管 SaaS。

## 2. 审阅结论

### 2.1 立得住的部分

1. **定位有真实空隙**：凭证在本地 + 手机能拍板，四象限里确实没人占。这不是"我觉得"，是 6 个竞品逐一核对后的结论。
2. **"默认自动化、零资质"的判断是对的**，而且被本机工厂的三份已验证实现（YouTube API / biliup / 网页自动化）反证过。
3. **状态机 + 事件 + 快照 source/status** 这套骨架能扛住"部分成功"这种最难的情况；`followup` 是正确的抽象，不是补丁。
4. **三层分离（内核 / 界面 / 通道）** 与"命令注册表派生三端"的组合，是防止三端漂移的少数可行方案。

### 2.2 站不住的部分（必须在 v0.1 前修）

| # | 问题 | 影响 | 处置 |
|---|---|---|---|
| **R1** | **契约与实现已经不一致**：`adapter-contract.md` 写 `capabilities.publish: "api" \| "web" \| "none"`、`visibility: Array \| null`，但 bilibili 适配器实际返回 `"web"`（其实是 biliup CLI）、还带了契约里没有的 `minScheduleLeadMs`；`PublishResult.state` 只允许 `published \| published_limited`，而发布模式有四种 | 下一个适配器（TikTok）会照错的契约写，第三次就会失控 | 立即改契约文档，把 `cli` 加进枚举、明确 `visibility` 语义（`[]` = 不支持，`null` = 未知）、补 `draft` 能力位 |
| **R2** | **账号健康检查没有链路**：PRD 承诺"提前 72h 告警"、F1 要求账号状态机由真实信号驱动，但架构里 `check` 只是 schema 注释，没有 handler、没有调度、适配器 `check` 是 `null` | G3 无法验收；用户仍然"到发布时才发现号掉了" | 定义 `check` 任务 + 适配器 `check()` 契约 + 采集/发布失败反向驱动，v0.1 必须合入 |
| **R3** | **followup 只有创建，没有核实**：PRD 写"系统自己核实（读回可见性/合集归属）"，架构里没有 verifier | "可追踪可关闭"退化成又一个 notes 字符串 | 定义 `followup.verify` 的 kind → 核实函数映射，先实现 `visibility` 与 `collection` 两个 |
| **R4** | **错误码没有枚举**：现在是 `auth_error` / `publish_failed` 随手写 | 卡片无法按原因给不同按钮，`doctor` 无法统计，排障只能读日志 | 定一张 error_code 表（auth / platform_reject / quota / flaky_ui / asset_invalid / unknown），映射到人话与处置动作 |
| **R5** | **时区没有约定**：`digest.daily 9:00`、按天聚合、快照日界线都没说用哪个时区 | 跨时区用户看到的"今天"是错的；对比曲线会漂一天 | 明确：**所有日界线用账号所属平台的主要时区**（国内 Asia/Shanghai，海外 UTC），存 UTC，展示按用户时区 |
| **R6** | **三端一致性只写在文档里**：没有 CI workflow，`commands-parity` 永远不会真的跑 | 这是架构的承重墙，没有测试就是在赌 | v0.1 必须加 `.github/workflows/ci.yml`：test + commands-parity + adapter-contract |

### 2.3 会拖慢开源的部分（v0.3 前处理）

| # | 问题 | 影响 |
|---|---|---|
| R7 | **全中文文档**：README、PRD、设计稿都是中文 | 海外创作者与贡献者在第一步就流失。开源第一屏必须有英文 README（其余可保持中文） |
| R8 | **三个名字并存**：`makerset`（品牌）、`fangyouxi`（组织）、`versekit`（产品） | 新人第一分钟就在猜它们的关系。README 需要一句话解释，或最终收敛成一个 |
| R9 | **`publish` 的唯一约束没解释**：`UNIQUE(work_id, account_id)` 意味着同一作品不能重复发到同一账号 | 用户"删了重发"会撞库。要么给 `republish` 命令，要么在文档里写明并给替代路径 |
| R10 | **没有速率预算**：runner 只保证同账号串行，没有"每账号每日发布上限 / 采集上限" | 平台风控与账号健康的下一个隐患 |

## 3. 里程碑与出门条件

> 每个里程碑只有在**出门条件全部可验证**后才算完成；对应 issue 见 GitHub Milestones。

| 里程碑 | 目标 | 出门条件 |
|---|---|---|
| **v0.1 内核闭环** | 一条内容能真的发出去、数据能回到本地 | ① TikTok + B站 两平台 `auto` 发出各 ≥1 条；② 失败能降级且 `fallback_reason` 正确；③ 快照落库且 `source/status` 正确；④ `check` 能主动发现失效；⑤ CI 跑通 test + commands-parity |
| **v0.2 控制面** | 手机上能拍板 | ① 飞书长连接配对成功；② 6 类必推事件可投递；③ 卡片按钮幂等 + 24h 过期；④ 账号墙能扫码登录；⑤ 失效能推卡片并被处理 |
| **v0.3 平台扩展** | 五个平台齐 + 可交付 | ① 小红书/抖音/YouTube 接入；② CSV 兜底；③ 看板可用；④ 英文 README；⑤ 外部用户盲测通过 G1/G2 |
| **v0.4 agent 化** | 能被 agent 组装 | ① Skill + MCP 双形态；② 飞书多维表格适配器；③ Telegram 通道 |

**排序原则**（比里程碑本身重要）：
1. 先做**会让人放弃**的环节（账号失效、发布失败），再做让人开心的（看板）。
2. 每个平台适配器都必须带 `collect`，否则"发布"就成了半个产品。
3. 每加一个平台，先补一条契约测试，再写实现。

## 4. 决策登记

| 决策 | 状态 | 结论 |
|---|---|---|
| 发布默认模式 | 已定 | `auto`，`notify` 仅作兜底 |
| 平台范围 | 已定 | YouTube / B站 / 抖音 / 小红书 / TikTok（Wave 1：YouTube·B站·小红书·TikTok） |
| 控制面首通道 | 已定 | 只做飞书，Telegram 延后 |
| 资质 | 已定 | 自动化路线零资质；官方 API 仅作升级项 |
| 复用策略 | 已定 | 移植流程、重写契约（ADR-0001） |
| **R1 契约修正** | 待办 | 改 `adapter-contract.md`（本文档同日登记） |
| **未定：是否支持"重发"** | 待定 | 影响 `publish` 唯一约束 |
| **未定：账号多开上限** | 待定 | 影响采集预算与风控策略 |
| **未定：托管版是否进路线图** | 待定 | 决定"凭证永不出本地"是不是永久承诺 |

## 5. 风险登记

| 风险 | 信号（什么时候你该紧张） | 缓解 |
|---|---|---|
| 平台改版导致自动化失效 | 某平台 `flaky_ui` 错误在一周内 > 3 次 | 适配器独立发版 + `collect.degraded` 事件 + 失败截图 |
| 登录态频繁失效 | `account.expiring` 日均 > 1 次 | 提前 72h 提醒 + 一键扫码 + 降低采集频率 |
| 通知噪音导致关闭通道 | 卡片 7 日点击率 < 10% | 合并投递 + 必推白名单（6 类）+ 默认静音 |
| 三端漂移 | `commands-parity` CI 失败 | R6 的 CI 是唯一防线，不能省 |
| 移植带进别人的假设 | review 出现 `assurelane`、固定 TID、期号规则 | ADR-0001 §6 的剥离清单 |
| 产品做成"自用的高级脚本" | 只有作者在用，`doctor` 全绿但没人发第二条 | G1 盲测：必须找外部创作者 |

## 6. 这份规划怎么用

- **issue 是唯一的执行单元**：任何工作先在 GitHub 上有 issue，再开分支；PR 描述里写 `Closes #n`。
- **里程碑不是日期，是门槛**：出门条件不满足就不发版，宁可推迟。
- **文档与代码同仓同提交**：改契约就改 `docs/adapter-contract.md`，否则下一次又出现 R1。
